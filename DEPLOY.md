# Deploying

The cutover to GitHub Actions is **done** (2026-08-07). This file describes the steady state, the
rollback, and the traps that are easy to walk into. For the historical one-time checklist, see this
file at commit `9ca64a7`.

Repo: **`ofektaiwan/website`** (public). Live at <https://www.ofektaiwan.com>.

---

## Steady state

Push to `main` and `.github/workflows/deploy.yml` builds and publishes. That is the whole flow.

```bash
git push origin main
gh run watch --repo ofektaiwan/website
```

To redeploy without a code change:

```bash
gh workflow run "Deploy to GitHub Pages" --repo ofektaiwan/website --ref main
```

The build runs `npm run build`, which is `astro check && astro build && check-i18n && check-css`. A
failing gate fails the deploy and leaves the currently published tree serving — a broken build cannot
take the site down.

## Rollback

`legacy-site` is a branch pinned at `720f816`, the exact pre-migration tree that served until the
cutover. Pages still remembers `source.branch = legacy-site`, so restoring it is one field:

```bash
gh api -X PUT repos/ofektaiwan/website/pages \
  -f build_type=legacy \
  -f cname=www.ofektaiwan.com \
  -F https_enforced=true
```

Then re-check the domain and HTTPS (below). To come back:

```bash
gh api -X PUT repos/ofektaiwan/website/pages \
  -f build_type=workflow \
  -f cname=www.ofektaiwan.com \
  -F https_enforced=true
```

**Never delete `legacy-site`.** It is both the rollback target and the only remaining copy of the 11
pre-migration commits — `main` was force-pushed over them, because this working copy was `git init`'d
from a zip and shared no history with the repo. (No content was lost: commit `0995c60` holds all 38
of those files at byte-identical blob SHAs.)

## After any Pages settings change ⚠️

Changing the Pages source can silently clear the custom domain or untick Enforce HTTPS. Re-adding a
cleared domain triggers certificate re-provisioning, which can mean **up to 24 hours** with no HTTPS.
Always pass `cname` and `https_enforced` explicitly in the same call — as the commands above do —
then confirm:

```bash
gh api repos/ofektaiwan/website/pages \
  --jq '{build_type, cname, https_enforced, cert: .https_certificate.state, expires: .https_certificate.expires_at}'
curl -sI https://www.ofektaiwan.com | head -3
```

Expect `cname: www.ofektaiwan.com`, `https_enforced: true`, `cert: approved`, and a 200. If the
domain field is empty, restore it *immediately* — the sooner it goes back, the more likely the
existing certificate is reused rather than reissued.

## Verifying a deploy

```bash
curl -sI https://www.ofektaiwan.com | head -4          # 200, fresh last-modified
curl -s  https://www.ofektaiwan.com/CNAME              # www.ofektaiwan.com
for p in / /zh-tw/ /robots.txt /sitemap.xml; do
  printf '%-14s -> ' "$p"; curl -s -o /dev/null -w '%{http_code}\n' "https://www.ofektaiwan.com$p"
done
```

Then confirm the scroll-driven scenes actually survived the CSS pipeline. `scripts/check-css.mjs`
guards this at build time, but this is the end-to-end proof:

```js
getComputedStyle(document.querySelector('.about-features-band')).animationName
// "scene-fade-out" = healthy   |   "none" = the Lightning CSS regression is back
```

**Run it in Chromium/Chrome/Edge, at ≥1440px, with reduced motion off.** In Safari or Firefox, or at
mobile width, or with reduced motion on, a perfectly healthy build reports `none` — the rules sit
behind `@supports (animation-timeline: view())` and `(prefers-reduced-motion: no-preference)`, and
`src/scripts/motion.ts` drives the same elements via WAAPI on non-supporting browsers. A healthy page
shows ~14 elements with a real `animationTimeline`; counting those is a stronger signal than any
single element.

Two non-issues that look like failures:

- **`/favicon.ico` 404s by design.** The site declares `/images/Ofek_favicon.ico` via
  `<link rel="icon">`, so browsers never fall back to the root path.
- **The sitemap is `/sitemap.xml`**, generated by `src/pages/sitemap.xml.ts`. There is no
  `@astrojs/sitemap` integration, so `/sitemap-index.xml` and `/sitemap-0.xml` correctly 404.

## Notes

- An Actions deploy **replaces the entire published tree**. `public/CNAME` is what keeps the custom
  domain working across deploys, so it must never be deleted, and the Pages custom-domain field must
  agree with it.
- `astro.config.mjs` `site` must stay `https://www.ofektaiwan.com`, `www` included — a mismatch
  produces canonical/OG URLs that 301 and split the SEO signal.
- **No `base` in `astro.config.mjs`.** On a custom domain it silently breaks every asset URL.
- `sharp` is an explicit dependency rather than left to Astro's optional resolution. Without that, a
  lockfile generated on macOS can omit the Linux binary the runner needs, and the image pipeline
  fails only in CI.
- The apex `ofektaiwan.com` is served by GoDaddy forwarding, not GitHub, and is **broken over
  HTTPS**. Unrelated to this deploy. The certificate covers `www` only.
